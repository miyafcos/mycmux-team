# decompose-guide — 分割設計 (品質最優先のタスク分解)

位置づけ: 「いつ割るか (残量)」でなく「**どう割るか (仕事の構造)**」。2026-07-30 宮崎さん裁定
「うまいこと分割するのが必要。品質最優先で」。残量ドリブンの fork 分裂 (会話を半ばで切る) は選ばない —
各子が「必要な文脈だけが濃く入った小さな spec」で走る状態が品質最大 (注意の希釈が無い)。

## 発火条件

重い依頼 = 次のいずれか: 素材投入型で対象が複数単位 (章・学年・科目・ファイル群) /
「まとめて・一括・全部・各〜」/ 3+工程の制作 / 手戻り10倍則の対象 (作問・組版・量産・外部送付)

## 運用モード (案件の重さで使い分け・2026-07-30 宮崎さん決定)

- **重い側 → 分割案を見せて GO**: 納品物・作問・組版・数十点量産・外部送付が絡む (R yes / M yes)。
  分割案は3〜5行 (単位 / 並列数 / 各完了条件 / 統合方法) で提示 → GO が出たら一気に走り切る
- **軽い側 → 全自動+事後報告**: 内部調査・検証・レポート・自環境整備 (R/U/M 全部 no)

## 分割原則 (品質を上げる切り方)

1. **独立性が絶対条件**: 相互依存する仕事を別の子に割らない。依存があるものは同じ子へ併合。
   「マージ判断が母艦に返ってくる分割」は品質を下げるだけなのでしない
2. **自然な単位で切る**: 章 / 学年 / 科目 / 大問 / 工程 / 検証観点。実測 (816本) では
   素材投入型 (>200k 率 44%) がこの切り方に最も適合する
3. **文脈は濃く小さく**: 各 spec は一次資料を直接読ませる自己完結型。親の会話履歴・要約を
   持ち込まない。「その仕事に要る文脈が全部あり、要らない文脈が無い」状態を作る
4. **完了条件は機械検証**: 単位ごとに実行コマンド / 照合手順。子の自己申告は成果でない
5. **統合・突合も新鮮なセッションで**: 全子の成果を横断チェックする「統合子」を最後に1本立てる
   (spec の接続先に全 DONE.md と成果物を列挙)。母艦は統合子の報告への裁定だけを持つ
6. **並列上限 3 は分割設計でも維持**: 単位が 4+ なら波で回す (第1波3本 → 検収 → 第2波)

## 手順

1. 依頼を単位に分解し、依存関係を確認 (依存があれば同一子へ併合)
2. R/U/M 判定 → 重い側なら分割案 3〜5 行を提示して GO を待つ / 軽い側なら即実行
3. 単位ごとに spec (spec-template.md 準拠) を並べる:
   `~/.claude/dispatch/<YYMMDD>-<slug>/spec-<単位>.md`
4. SKILL.md 手順 2 の spawn を並列上限内で発射・台帳記録 (1 単位 = 1 行)
5. DONE 回収 → 親検収 (dispatch_status.py + 実体検証)
6. 統合子を spawn → 統合報告に母艦が裁定
7. spec-lock 対象 (作問・スライド・量産) は**分割設計自体を lock してから** 3. へ進む

## アンチパターン (やらない)

- 残量が減ってから慌てて fork で半分に切る (切れ目が恣意的で両片とも文脈が中途半端)
- 均等 N 分割 (行数・ページ数で機械的に割る) — 自然な境界を跨ぐと検収が壊れる
- 親が全子の成果物を自分で読み込んで統合する (母艦が重くなり分散の意味が消える)
- 複製ボタン (fork) を分割の代用にする — fork は「同じ文脈で別の議論をしたい」とき専用
