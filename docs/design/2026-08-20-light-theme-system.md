## 1. 何を直すのか

指摘は「ライト系の色のバランスが全体におかしい」だった。調べた結論は、
**9本の配色が悪いのではなく、検証した色と画面に出る色が別物になっている**こと。

テストは `themeContrast.test.ts` で1テーマ31ペア・9本で279ペアを検査し、全部通っている。
しかし検査対象は**不透明な16進数どうし**で、実際の描画はそのあとに

- 壁紙の上への alpha 合成 (パネル 0.68 / ターミナル 0.62 / 黒幕 0.08)
- コンポーネント内の `color-mix()` (透明へ向かう混色を含む)
- コンポーネント内の直値 (98箇所)
- ダーク前提のフォールバック値 (`var(--x, #161616)` 等)
- 未定義トークンのフォールバック (`--status-warning` は定義が存在しない)
- xterm 独自のコントラスト経路 (壁紙ON時は補正が切れる)

を通る。**最終的に描画される色を持っている層が存在しない**。63本の CSS 変数は最終パレットではなく、
「63本 + コンポーネントの例外98箇所 + 背景の状態 + xterm の挙動」が最終パレット。これが根本原因。

したがって修正は「ライト分岐を改善する」ではなく、
**確定した最終テーマ (resolved theme) を1箇所で作り、全コンポーネントをその下位に置く**こと。

---

## 2. 目標とする構造

```
ThemeDefinition      … 作者が書いた不透明な色のアンカー (alpha を持たない)
      ↓
CompositionPolicy    … 壁紙の色調と、最上位コンテナだけが持つ背面 alpha
      ↓
ResolvedTheme        … コンポーネントが消費する最終セマンティック色 (全部不透明)
      ↓
コンポーネント        … 色計算をしない・直値を持たない・暗黙フォールバックを持たない
```

現状はこの境界が存在しない。まずこの境界を作る。

## 3. 面の階層 (Q1 の裁定)

### 決定

持ち上がった面を暗くする現行を**やめる**。`background` は階層の1段目ではなく
**canvas (地)** として階層の外に置く。面の基準は paper (= 現行の `chrome.surface`) 1つ。

| ロール | 導出 | 用途 |
|---|---|---|
| `canvas` | 現行 `chrome.background` | アプリの地・隙間・壁紙の下地 |
| `surface-low` | paper から canvas へ OKLCH で 40% 寄せる | 後退するクローム |
| `surface` | 現行 `chrome.surface` (paper アンカー) | 主コンテンツ面 |
| `surface-raised` | paper と同色 | 持ち上げ面。段差は細罫と影で出す |
| `popover` | paper と同色・完全不透明 | メニュー・ポップオーバー |

不変条件:

```
L(canvas) < L(surface-low) < L(surface) ≤ L(surface-raised) ≤ L(popover)
```

上3つが等しいのは意図的。paper は既にほぼ白で、正のオフセットを足すとテーマごとに
クリップ量が変わる (墨昼は余地ゼロ、生成りは余地あり) ため、1つの規則から9通りの
段差が生まれてしまう。**段差は明度ではなく細罫と影で出す**。

### 根拠

9本の paper と canvas の OKLCH 明度差は **0.0597〜0.0654** に収まっていた (実測)。
9本が既に同じ間隔を持っているので、`surface-low` をその 40% に置く規則が
9本すべてにそのまま適用できる。

現行の値では、明るさの並びが9本すべてで
`canvas < popover < surface-raised < surface` になっている。
いちばん高いはずのポップオーバーが平場より沈んでいる。

### 現行を残す側の言い分と、それでも退ける理由

paper がほぼ白のとき、暗くする方が影に依存せず差を作れる — これは正しい。
それでも退ける理由は、canvas が既に暗い側にあるため、**同じ明度軸が
「奥に引っ込む」と「手前に浮く」の両方を意味してしまう**こと。壁紙の alpha が
絡むとこの多義性は機械検証が不可能になる。

## 4. 壁紙合成 (Q2 の裁定)

### 決定 — 選択肢 (d)

**上限つきの半透明 + テーマ配色に沿った壁紙の色調補正**。壁紙のサンプリングを
安全装置にしない (後述)。

`imageDim` (0〜1・黒のみ) を廃止し、符号つきの **`wallpaperTone`** に置き換える。

- 負 = 黒へ寄せる
- 正 = **そのテーマの paper 色**へ寄せる (白ではない)
- 0 = 素のまま

ダーク側は現行の黒 0.08 を `wallpaperTone = -0.08` に読み替えれば描画結果が変わらない。
ライト側の既定は `+0.10`。paper へ寄せるので、生成りは暖色のまま、桜は桃色のまま濁らない。

### ライトの既定値

| 設定 | ライト既定 | 現行 |
|---|---:|---:|
| 壁紙の不透明度 | 1.00 | 1.00 |
| `wallpaperTone` | **+0.10** (paper へ) | `imageDim` 0.08 (黒へ) |
| クローム背面 alpha | **0.80** | 0.68 |
| ターミナル背面 alpha | **0.86** | 0.62 |
| 持ち上げ面 | **1.00** | 0.68 |
| ポップオーバー | 1.00 | 1.00 (現行も不透明) |

> **2026-08-21 追記 — この表は全面的に撤回済み (§12)。**
> 実装の現行値は クローム 0.68 / ターミナル 0.62 / 持ち上げ面 0.68 (= 利用者の設定そのまま)、
> `wallpaperTone` は **-0.08 (8% 黒)・ライトもダークも同じ**。
> **純黒に対するコントラスト保証は撤回した** — 不透明度で買うと壁紙が隠れ、
> 色調で買うと壁紙が漂白される (実測 58.6 → 109.6)。詳細は §12。

### この値の根拠 (最悪ケース = 純黒の壁紙)

壁紙は「最悪でも純黒」で押さえられる。source-over 合成では RGB が負にならないため、
**純黒より暗い背面は原理的に作れない**。よって純黒に対して通れば全壁紙で通る。
サンプリングが要らないのはこのため。

純黒に対する実測 (`wallpaperTone` の効果は入れていないので保守的):

| | 最弱のテーマ | 比 |
|---|---|---:|
| paper 面 @0.80 の本文 | 生成り | **6.11:1** |
| `surface-low` @0.80 の本文 | 生成り | **5.70:1** |
| ターミナル @0.86 の本文 | 生成り | **7.09:1** |

壁紙の寄与は クローム 20% / ターミナル 14%、色調補正後で実質 18% / 12.6%。
壁紙は見えるが、**文字色の共著者ではなくなる**。

### 何がコントラストを保証するか — 面と文字の両方

**面の側** — 半透明を許すのは指定した最上位コンテナだけ。
セマンティックな面トークンはすべて不透明にする。
`colorWithOpacity()` を全面トークンに掛ける現行をやめ、
`chromeBackdrop` / `terminalBackdrop` という別ロールに alpha を隔離する。

**文字の側** — 前景は必ず不透明。`text` / `textSecondary` / `textTertiary` /
状態色の前景 / エージェント色 / ANSI 16色に alpha を持たせない。
さらにライトでは、半透明の面に載る前景に極性の条件を課す:

```
Y(前景) < Y(その面を純黒の上に合成したときの輝度)
```

これを満たせば純黒が厳密な最悪ケースになり、サンプリングなしで機械保証できる。

### 床値

| 対象 | 床 |
|---|---|
| 情報を伝える文字すべて (11px のサイドバー見出しを含む) | **4.5:1** |
| 二次・三次テキストとターミナル本文の生成目標 | 5.0:1 (合否判定は 4.5:1) |
| 機能アイコン・フォーカス表示・コントロールの境界 | 3.0:1 |
| ベタ塗りバッジの文字 | 4.5:1 (バッジの塗りに対して) |

一次・二次・三次の差は**不透明な明度差・太さ・大きさ・余白**で作る。
背面が不定のところで透明度を階層に使うのは、階層ではなく先送りされた不具合。

### 他の選択肢を採らない理由

- **(a) 幕を白黒二値にするだけ** — 黒のみよりは良いが不十分。テーマの明暗は
  壁紙が明るいか暗いかを教えてくれないし、透明な文字は直らない
- **(b) 不透明度を上げるだけ** — 堅牢で安いが、コンポーネント内の透明文字・
  エージェント直値・ターミナルの ANSI 計算が壊れたまま残る
- **(c) サンプリングを主機構にする** — 平均輝度では保証にならない (既定壁紙は平均 0.029 だが
  下位5%点は 0.003)。領域サンプリングは可能だが、クロップ・キャッシュ・レイアウト依存を
  抱え込む。alpha の床を決めるだけで済む話に対して機構が重すぎる

サンプリングは後から**見た目の最適化**として足すのはよい。足すなら、実際の cover クロップ後の
タイル単位の輝度包絡か領域パーセンタイルを使い、同じコントラスト計算器が安全と証明した
ときだけ alpha を下げる。

### 補足: `tone` メタデータは判定に使えない (この設計メモでの実測)

カタログの `tone` タグ (`dark` 18 / `mid` 29 / `bright` 12) は実際の平均輝度と一致しない。

- `tone: "bright"` の `lumon` は平均輝度 **0.020** (ほぼ黒)
- `tone: "mid"` に平均 0.018 の `grafbase` が入っている
- 3つのタグの輝度範囲がほぼ完全に重なる (dark 0.022–0.363 / mid 0.018–0.456 / bright 0.020–0.773)

よって「`tone` を見て既定を切り替える」実装は採らない。

## 5. 要素の割り当て (Q3 の裁定)

### 決定

**サイドバーはターミナルより下**。「下」は暗い不透明な色調であって、透明度が高いことではない。

| 要素 | 面ロール | 背面 alpha |
|---|---|---:|
| アプリの地・隙間 | `canvas` + 壁紙 | — |
| タイトルバー | `surface-low` | 0.80 |
| サイドバー | `surface-low` | 0.80 |
| ペインタブ帯 | `surface-low` | 0.80 |
| 非選択のペインタブ | `surface-low` | 継承 |
| 選択中のペインタブ | `surface` | 不透明、またはターミナル面と視覚的に連続 |
| ターミナルペイン | `surface` | 0.86 |
| インラインの持ち上げ面 | `surface-raised` | 1.00 |
| ポップオーバー・メニュー | `popover` | 1.00 |

選択中のタブは**ターミナル面とつながって見える**べきで、ターミナルの上に浮く物ではない。
選択状態であって高さではないので `surface-raised` は意味的に誤り。

選択行・ホバー行・アクティブペイン表示・フォーカス表示も**状態**であって階層の段ではない。
`hover` / `selected` / `focus` はホスト面に対する**不透明色として生成**し、
コンポーネント側で混色しない。

### `TabBar` のローカル上書きは削除する

```
color-mix(in srgb, var(--cmux-text) 58%, transparent)
```

これをトークン化するだけでは不可。**不正な演算に立派な便箋を与えるだけ**。

移行手順:

1. 現行の `textMuted` / `textDim` の値を「希望値」として扱う
2. 不透明色として解決する
3. **許可されたすべての面に対して**役割ごとの目標を満たすところまで暗くする
4. 将来的には `textMuted` / `textDim` を任意のヒントに降格し、
   `textSecondary` / `textTertiary` は `text` とホスト面から導出する

11px の見出しは情報を伝える文字なので 4.5:1 が最低、生成目標 5.0:1。
「三次」は「壁紙が味方したときだけ読める」という意味ではない。

### 状態色

状態色は階層に属さない。各状態が役割の族を持つ:

- `status.<kind>.foreground` — 中立面の上の文字・アイコン
- `status.<kind>.subtleBackground` — ホスト面に対して導出した不透明色
- `status.<kind>.strongBackground` — ベタ塗りバッジ用
- `status.<kind>.onStrong` — ベタ塗りバッジの文字色

解決器はライトの状態色前景を、`surface-low` と `surface` の**両方**で通るまで暗くする。

`--status-warning` を `waiting` に黙って別名付けしない。消費側2箇所が本当に
「入力待ち」を表しているなら消費側を `status-waiting` に直す。「注意」を表しているなら
`warning` を正式な状態ロールとして追加する。

**消費されているのに定義されていないトークンは CI で落とす**。琥珀色の直値を
どこからか召喚するのではなく。

### 危険色とエージェントバッジ

ベタ塗りのセマンティック色にはすべて `on-*` トークンが要る。共通の `#c85757` に対しては

- 白 = **4.24:1** → 不合格
- 黒 = **4.96:1** → 合格

したがって更新バッジは解決済みの `on-error` を使い、解決器はこの塗りに対して黒を選ぶ。
白文字が譲れない要件なら、解決器が塗りの側を暗くする。直値の `white` は判断ではない。

エージェント種別バッジは全種・全テーマで1つの規則にする:

1. エージェントの色相をホストの paper に混ぜて不透明な subtle 背景を作る
2. 同じ色相のまま OKLCH 明度を下げ、4.5:1 に達するまで動かす
3. ベタ塗りを使うなら `onAgent` を別に導出する

これで45組すべてが9本の分岐なしに直る。

## 6. 微調整後のクランプ (Q4 の裁定)

### 決定

`applyThemeTweaks()` に現行の破壊的クランプを**再実行させない**。
代わりにパイプラインを1本の最終パスに置き換える。

1. 基底定義とユーザー微調整を合成して **authored theme** を作る
2. 全色を解析・正規化する
3. 作者が書いていない派生トークンを導出する
4. 合成ポリシーを解決する
5. **描画されるコントラストのグラフを検証する**
6. `ResolvedTheme` と構造化された診断を出す

`authored` (ユーザーが入れたそのもの) と `resolved` (コンポーネントが消費するもの) の
両方を保持する。

解決器が自動で変えてよいのは**派生トークンだけ** (`on-error`・不透明な hover 塗り・
導出した二次テキスト・エージェント前景・ANSI 補正)。
`paper` / `text` / `accent` / 直接編集された状態色といった**明示的なアンカーは黙って変えない**。

明示的な不合格の扱い:

- 組み込みテーマ → **CI で落とす**。例外なし
- ローカルのユーザーテーマ → ペアごとの警告と実測比をその場で出す
- 危険なローカルテーマの適用・保存 → `allowUnsafeContrast` の明示的な承諾を要求
- 書き出し・配布するテーマ → 検証で落とすか、危険であることを明示する

黙って直すのは色編集器を不誠実にする (入れた色と違う色が出て、どのフィールドが
なぜ動いたか説明できない)。見える検証失敗の方がまし。

### 色入力の契約も変える

- 16進数 / `rgb()` / `rgba()` / `hsl()` などを正規表現でなく**正規の色表現に解析**する
- 解析できない値を「ダーク」と分類**しない** (現行は非16進数を暗黙にダーク扱いにしている)
- 不正な構文は拒否する
- パレットのアンカーは alpha 1.0 必須。透明度は `CompositionPolicy` の管轄

## 7. 追加で直す3点 (Oracle が本体と併せて挙げたもの)

1. **宣言された `scheme` を正とする。** BT.601 輝度は診断には使ってよいが、
   分岐の決定に使わない。暗い canvas に明るい paper を意図的に組み合わせたテーマが
   あり得る。現行は `chrome.background` の輝度 140 だけで19本のトークンが切り替わる

2. **ダークの影テーマを消す。** トークン一式が保証されたら、コンポーネントの
   `var()` から第2引数の直値を消す。初回描画は、保存済み設定から `data-scheme="light|dark"` を
   同期的に立て、scheme ごとに完全な起動パレットを1つ用意する。
   変数の欠落は開発時テストで落とす。黙って暗い灰色にならない

3. **ターミナルを実効背景に対して直す。** 独自の ANSI 床は、作者が書いた不透明な
   `terminal.background` ではなく、**描画されうる最も暗いターミナル面**に対して解決する。
   xterm 内蔵の比を 1 のままにしてよいのは、代替の解決器が合成後の不変条件を
   本当に強制している場合だけ

## 8. 実装が満たすべき機械的な受け入れ条件

1. ライト全テーマで `L(canvas) < L(surface-low) < L(surface) ≤ L(raised) ≤ L(popover)`
2. セマンティックな前景・面トークンがすべて不透明。alpha を許すのは
   背面ロールと影ロールだけ
3. 前景と面の組み合わせすべてを、**実際の sRGB 合成経路を通して**検査する。
   ライトの最上位パネルは**純黒の壁紙**に対して検査する (最悪ケースの上界)
4. 情報を伝える文字のペアがすべて 4.5:1 を通る。ターミナル前景と解決済み ANSI 16色が
   実効ターミナル背景に対して目標を通る。文字でない機能表示が 3.0:1 を通る
5. 静的検査で次がゼロ:
   - 宣言なしに消費されている変数
   - コンポーネント内の生の前景・背景・罫線・塗り・線の直値
   - コンポーネント内の `transparent` を含む `color-mix()`
   - `var(--token, ダークの直値)` 形式のフォールバック
   - `on-*` の代わりに直値の白・黒を使っているベタ塗り
6. 代表的な正常・異常のユーザー微調整を合成後に適用し、
   合格した `ResolvedTheme` か正確な診断のどちらかが出ることを検証する。
   **構文が scheme 分類を変えてはならない**
7. ダークの解決後の比は既存のラチェットで凍結したまま。当面はダークの導出経路を
   実務上可能な範囲でバイト単位で据え置き、宣言された light テーマだけを
   新しい面・合成ポリシーへ通す

## 9. 着手順序と「この判断が誤りだと分かる条件」

### 段1: authored → resolved の境界を作る

色の導出・不透明度ポリシー・`on-*` の選択・診断をすべて純粋な解決器へ移す。

> **誤りだと分かる条件**: computed style の監査で、正当なコンポーネント状態が
> 扱いきれる規模のセマンティックトークン集合では表現できない色変換を
> 日常的に必要としていると判明した場合。トークン分類が粗すぎることを意味する。

### 段2: ライトの役割割り当てと合成既定値を同時に出す

`surface-low` をクロームへ、paper をターミナルへ、持ち上げ面とポップオーバーを不透明に、
`panelOpacity 0.80` / `terminalOpacity 0.86` / `wallpaperTone +0.10`。

> **誤りだと分かる条件**: 暗い・中間・明るい壁紙の比較で、利用者が壁紙を認識できない
> または価値を感じなくなり、かつ**より低い不透明度でも最悪ケースの合成テストを通る**と
> 分かった場合。そのときは適応サンプリングで安全な透明度を回収する。

### 段3: 消費層から色の権限を取り上げ、微調整後の診断を足す

透明混色・直値・ダークのフォールバック・未定義トークンのフォールバック・
作者背景基準の ANSI 計算を除去する。

> **誤りだと分かる条件**: テーマ作者が明示アンカーの自動修正を繰り返し好み、
> 「警告 + 承諾」の方が分かりにくいと感じた場合。既定ONの「コントラスト保護」
> モードを可視化する理由にはなるが、それでも黙って書き換える理由にはならない。

## 12. 純黒保証の撤回 — 段2 / 段2b をどちらも戻した (2026-08-21)

**結論を先に。純黒の壁紙に対するコントラスト保証と、このアプリのガラスの見た目は両立しない。
保証の側を捨てた。** 保証はこのメモが持ち込んだもので、宮崎さんは一度も求めていない。

### 経緯 — 同じ保証を2通りの通貨で買い、2回とも却下された

| | 保証の買い方 | 実機での結果 |
|---|---|---|
| 段2 (`6d44794`) | 不透明度を上げる (クローム 0.80 / ターミナル 0.86・持ち上げ面とポップオーバーを不透明) | **壁紙が見えなくなった。** 「板の上に文字が乗っている感じ」で却下 |
| 段2b | 色調 `wallpaperTone` をライトだけ **+0.25** (paper へ) | **壁紙が漂白された。** 見えてはいるが色が飛ぶ |

段2bの実測 (宮崎さんのテスト機の実際の組み合わせ = 朝凪 + `oppenheimer`):

> **画像の平均輝度 58.6 → 109.6。** 黒が灰桃色に浮き、絵が平板になる。

paper がほぼ白なので、「テーマの色へ寄せる」は実質「白へ寄せる」だった。
段2は壁紙を**隠し**、段2bは壁紙を**漂白した**。どちらも宮崎さんが作り込んだものを壊している。

### なぜ保証そのものを捨てるのか

純黒は「壁紙がどれだけ暗くなりうるか」の**真の上界**であると同時に**無意味な目標**でもある。

- 同梱の壁紙はどれも純黒の近くにない
- 利用者は自分が読める壁紙を選ぶ。読めなければ壁紙か不透明度を変える (どちらもスライダーがある)
- この上界にパレットを縛ると、**壁紙の可視性か色のどちらかを必ず支払う**ことになる (上の表が実証)

支払う価値のある保証ではない。**利用者の見た目を出荷するのが正しい判断。**

### 何を戻したか

| クローム背面 alpha | 利用者の設定 (既定 0.68) |
| ターミナル背面 alpha | 利用者の設定 (既定 0.62) |
| 持ち上げ面 | パネルと同じ |
| 壁紙の幕 | **8% 黒・ライトもダークも同じ** (`wallpaperTone = -0.08`) |
| hover / selected | 作者が書いた wash そのまま |
| 文字4段の導出先 | **テーマが定義した不透明な面** (合成後の面ではない) |

`LIGHT_DEFAULT_WALLPAPER_TONE` とライト側の読み替えは削除した。
読み替えには**保存値を捨てる**という別の不具合もあり、ライトテーマでは
色調スライダーを動かしても何も起きなかった (`resolveWallpaperTone` が既定値のとき
常に +0.25 を返していたため)。スライダーは1本・値は1つ・両スキーム共通に戻した。
