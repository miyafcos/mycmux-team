## 1. 現状 — タブ5本、その前に階層が崩れている

| タブ | 実体 | データ源 | 実装 |
|---|---|---|---|
| 使用量 | 日別チャート・モデル別表・時間帯リズム・トータル | SQL 集計のみ | `UsageView.tsx` |
| 振り返り | 日次ダイジェスト (日付送りあり) | LLM 要約 | `DigestView.tsx` |
| 学び | 原因/制約/ハマり/決定/検証済 + 失敗コマンド上位 + 書き直しファイル上位 | LLM 要約 + SQL | `LearningView.tsx` |
| 実験 | 効率比較 + ルール通信簿 | SQL 集計のみ | `ExperimentView.tsx` |
| 詳細 | 期間バー・サマリー・ヒートマップ・関係図・モデル/案件/セッション表 | SQL 集計のみ | `AiLogPanel.tsx:334-490` にインライン |

### 崩れている点 (統合前に直さないと持ち越す)

1. **「使用量」が面の名と指標名を兼ねている** — 日別チャートは「ターン数 / 使用量」を切り替える
   (`UsageDailyChart.tsx:53`)。層が違うものに同じ語を当てているので、面に何を足しても意味が濁る
2. **「振り返り」と「学び」が包含関係** — 日本語として振り返り ⊃ 学び。並列のタブにならない
3. **「実験」が実体と合っていない** — 中身は条件別の効率比較。実験はしていない
4. **「詳細」が何の詳細か言っていない** — 実体は期間分析の全部。別にセッション詳細も存在する
5. **1つの面の中で出どころが混ざる** — 「学び」は要約由来の findings と集計由来のランキングが同居し、
   行を見てもどちらか分からない
6. **指標語の揺れ** — コスト / コスト相当 / コスト算入外、キャッシュ率 / キャッシュヒット率

## 2. 語彙の方針 (v3 の中心)

**画面に出る言葉は、宮崎さんが実際に使っている言葉から採る。** 設計者の美学 (漢語で短く揃える等)
を優先しない。読んで分かるまでに学習が要る語は、それだけで画面の摩擦になる。

| 層 | 何を書くか | 文体 | 例 |
|---|---|---|---|
| **面** (タブ) | その面に何があるか | 日常語の名詞句 | 使った量 / わかったこと |
| **段** (面の中の区切り) | その段が答える問い | 問いの短文 | いつ・どれだけ / 何に / 使い方で変わる？ |
| **節** (段の中の見出し) | 何を並べているか | 対象の名前 (問いにしない) | 案件別 / モデル別 / effort |
| **指標** (列・切替) | 数え方 | 単位を含む短語 | コスト相当 / ターン数 / キャッシュ率 |
| **データ** (型・保存・socket) | 実装の識別子 | 英語 | `record` / `insight` / `declared` |

- **問いを持つのは段だけ**。現行は節に問いが散っている (「長いセッションは損？」
  「effort を上げると見合っている？」)。問いを段に集約し、節は対象名に統一する
- **層をまたいで同じ語を使わない**。破れ1 (面の名=指標名) の再発防止
- **日本語を識別子にしない / 英語を画面に出さない**

## 3. 面 — 2つ

分割の軸は**その数字がどこから来たか**。機械が数えた事実と、要約が書いた解釈は、正しさの性質が
違う。混ぜると「これはどこまで信じてよいか」が読み手から見えなくなる。

| 面 | 画面の名前 | 中身 | 空になり得るか | 識別子 |
|---|---|---|---|---|
| 面1 | **使った量** | ログから機械的に数えた事実 (LLM を介さない) | ならない | `record` |
| 面2 | **わかったこと** | ログを要約して得た解釈 (LLM 由来) | なる (要約が進むまで) | `insight` |

却下した名前と理由: 「使用量」(指標名と衝突) / 「振り返り」(「学び」を含む) / 「分析」(両面とも分析) /
「詳細」(何のか言っていない) / 「実験」(実験していない) / 「実績」「気づき」(短いが業務文書の語感で、
宮崎さんが普段使う語ではない)。

## 4. 段 — 各面に3つ

### 面1「使った量」

| 段 (問い) | 中身 | 現行のどれ |
|---|---|---|
| **いつ・どれだけ** | トータル・日別チャート・時間帯リズム | 使用量 |
| **何に** | ヒートマップ・関係図・案件別・モデル別・セッション一覧 | 詳細 |
| **使い方で変わる？** | effort・compact・サブエージェント・セッションの長さ・ルール通信簿 | 実験 |

「使い方で変わる？」の下の節は、現行の疑問文タイトルを対象名に直す
(「effort を上げると見合っている？」→ 節「effort」、「長いセッションは損？」→ 節「セッションの長さ」)。
問いは段が1つ持ち、節は何を並べているかだけを言う。

### 面2「わかったこと」

| 段 (問い) | 中身 | 現行のどれ |
|---|---|---|
| **その日のまとめ** | 日次ダイジェスト (日付送りそのまま) | 振り返り |
| **何度も起きてること** | ハマり・原因 + 失敗コマンド上位 + 書き直しファイル上位 | 学び (の一部) |
| **決めたこと** | 決定・制約・検証済 | 学び (の一部) |

現行「学び」を問い単位で2段に割り直す。**集計由来のランキング (失敗コマンド上位・書き直しファイル上位)
が「何度も起きてること」に入るのは問いが同じだから** — ただし出どころが違うので、行に
`数えた` / `要約` のチップを必ず付ける。面の分割軸を段の中で破らないための措置。

**分類チップの語を段名と重ねない**: 段「決めたこと」の中に分類「決定」が出ると入れ子の同義になる
(`LearningView.tsx:13-15` の `decision: "決定"`)。チップ側を動詞形に変えて衝突を外す —
`決めた` / `制約` / `確かめた`、「何度も起きてること」側は `ハマり` / `原因`。

## 5. 関係性 (面と面・面と末端)

- **末端はセッション詳細** (`SessionDetailView.tsx`)。オーバーレイのままで、面に昇格させない。
  両面のどの行からも開ける
- **使った量 → わかったこと**: 数字が跳ねた日の行から、その日の「その日のまとめ」へ
- **わかったこと → 使った量**: 何度も起きている罠の行から、その日の「何に」へ
- **期間は面をまたいで1つ**。期間バーは「使った量」に1本だけ置き、面を切り替えても選択期間を保つ
  (現行は「詳細」の中にあり、他の面から動かせない)

## 6. 語の一意化 (統合と同時に揃える)

| 使う語 | 意味 | 使わない語 | 理由 |
|---|---|---|---|
| コスト相当 | 公表料率×トークンの推定額 (実請求ではない) | 「コスト」単独 | 推定であることが消える |
| 算入外 | 単価未設定でコスト相当に入っていない分 | 「コスト算入外」 | 冗長。文脈で自明 |
| キャッシュ率 | 入力のうちキャッシュ読みが占める割合 | 「キャッシュヒット率」 | 同義の二重語 |
| ターン | 指示と応答の1往復 | — | — |
| 手戻り | 同じファイルの書き直し・失敗の再実行 | 「リワーク」 | — |
| 案件 | project | 「プロジェクト」 | — |
| 中断率 | ツール実行のまま終わったセッションの割合 | 「放棄率」 | 責める語感を避ける |

空表示の文言は「**なぜ空か + 何をすれば出るか**」を必ず書く (現行「該当する学びはまだありません
(要約が進むと増えます)」はこの型を満たしている。他の空表示もこの型へ揃える)。

## 7. 統合と同時に守ること (退行防止)

- **LLM は明示操作でしか回さない**。現行は「振り返り」タブを開くと自動でダイジェスト生成が走る
  (`AiLogPanel.tsx:150-162`)。統合後は「わかったこと」を開いた時点で走ることになり、**「何度も
  起きてること」を見たいだけで LLM が回る**。自動生成はボタン (または明示設定) へ寄せる。
  ailog パネルが開くだけで LLM を回していた不具合を直した経緯があり、同じ穴を作り直さない
- **段ごとの遅延読み込みを維持**。現行は view ごとに `refreshUsage` / `refreshLearning` /
  `refreshExperiment` を出し分けている (`AiLogPanel.tsx:122-142`)。統合後も見えている段だけ取得する

## 8.5 v4 改訂 (2026-08-14 夜 — v0.38.0 実機FBによる立て直し・この節が §2/§4 の該当箇所を上書きする)

v0.38.0 を実際に触った宮崎さんのFB「期間ずらしても反映されん・待たされてるのか不明・長い・
項目が意味不明・切り替わり不十分」を受けた確定変更。2面構造は維持。

### 命名 (問い形式の廃止 — Q1 は「否」で決着)

段名を問い文にする v3 の実験は実地で失敗。**画面のラベルは全層で普通の名詞**にする。

| 面 | 段 (旧 → 新) |
|---|---|
| 使った量 | いつ・どれだけ → **全体** / 何に → **内訳** / 使い方で変わる？ → **比較** |
| わかったこと | その日のまとめ → **日別まとめ** / 何度も起きてること → **繰り返しの罠** / 決めたこと → **決定事項** |

導線ボタンは「日別まとめへ」「その日の内訳へ」。

### 応答性 (最重要 — 操作から 300ms 以内に画面が反応する)

- **データが表示済みでも、再取得中は既存コンテンツを減光 (opacity 約0.55) し、コンテンツ直上に
  細い「更新中…」バーを出す**。skeleton は初回 (データなし) のみ、というのは変えない
- ヘッダーの状態表示は**可視の面・段の loading フラグ**を反映する (別段のフラグを見ない)
- 段切替時: 新しい段にデータが無ければ即 skeleton、古い期間のデータが残っていれば減光+更新中。
  無言で旧内容が据え置かれる状態を作らない
- 段ボタンの選択状態は塗りで明示 (aria-pressed=true をアクセントの塗りに)

### 長さ (1段 = 1〜1.5画面)

- **全体** = トータル+日別チャートのみ。稼働リズムは閉じた `<details>`
- **内訳** = サマリー+モデル別・案件別・セッション表。ヒートマップ・関係図・単価設定は
  閉じた `<details>`
- 段の中身が3ブロックを超える分は `<details>` へ (本文の折りたたみ禁止則の例外として、
  ailog の探索系ブロックは可とする)

## 8.6 v5 改訂 (2026-08-14 — 単価まわりの設定項目ゼロ化・宮崎さん指示「黄色の警告が出ないよう0ベースで」)

「単価未登録」という状態と、それを謝る黄色バナー・単価設定 UI を廃止する。

### モデルの自動分類 (backend が price 解決時に判定)

| class | 判定 | コスト扱い |
|---|---|---|
| `priced` | 内蔵カタログに料率あり | 従来どおり計上 |
| `local` | モデル名が `ollama/` 等のローカル系 prefix | $0 が事実 (「ローカル実行 — 費用なし」) |
| `internal` | `<synthetic>` 等の内部生成行 | コスト概念の対象外 |
| `flat` | 定額サブスク (fugu 系) | 従量費用なし (「定額枠」) |
| `unknown` | 上記以外で料率なし (旧世代クラウド等) | 推定捏造はせず除外。ただし警告でなく下記の刻み方 |

### 表示の原則 (階層)

1. **注釈は修飾する数字の隣に置く**。全幅の警告バナー (RangeBar 下の黄色文・UsageTotals の「算入外」カード) は廃止
2. `unknown` があるときはコスト相当のラベル自体を正直化する:
   「コスト相当 $X (単価既知の NN% 分)」— NN = priced+local+flat が **internal を除く**
   総トークンに占める割合 (内部生成はコスト概念の対象外なので分母に入れない)。
   100% のときは付記なし
3. 行レベル: `unknown` の行のコストセルは「—」+ツールチップ「単価未公表のため除外」。
   `local`/`flat` は $0 +ツールチップで理由
4. **単価設定 UI (PriceSettings) は撤去**。設定項目ゼロ。手動単価テーブルは backend に残ってよいが
   UI からは触れない

## 8.7 v6 改訂 (2026-08-14 — 1面化と操作列の再設計・宮崎さん実機FB第2便)

FB:「やっぱり1つにまとめよう。結局それぞれの中で入れ子のページができていて2つに分けた意味がない」
「用語にこだわれ。トータル・ファミリー・モデル名・日・週…の並びが意味わからん」

### 1面化 (§3 の2面を撤回)

- 面の切替 (使った量/わかったこと) を廃止し、**段バーを1本**にする:
  `全体 / 内訳 / 比較 ｜ 日別まとめ / 繰り返しの罠 / 決定事項` (集計系と要約系の間に
  細い区切りのみ。ナビゲーションは1階層)
- 期間バーは常時表示 (旧 record 面限定を解除)。日別まとめの日付送りは従来どおり段内。
- 識別子 `record` / `insight` は内部に残してよい (表示上の面だけ廃止)。
  LLM 明示起動・段別遅延読み込み・更新中表示の契約は不変。

### 操作列の再設計 (「どの表示を操作するボタンか」を場所と語で示す)

原則: **コントロールは、それが効く表示の直上に置き、必ず日本語の役割ラベルを先頭に付ける**。
無関係なトグルを1行に混ぜない。

- 「トータル」節: 指標選択のみを持つ — `指標: 入出力トークン / 総トークン / ターン数 / セッション数`
  (指標はトータル・日別・モデル別すべてに効くため、節タイトル直下で最上段に1つ)
- 「日別」節 (チャート直上): `単位: 日 / 週 / 月`　`表示: 実数 / 構成比`　`まとめ方: 系統 / モデル`
  (旧「ファミリー/モデル名」→「系統/モデル」。「バケット」という語は画面に出さない)
- 鮮度チップ (「記録は◯◯まで」)・再インデックスはチャート節でなく期間バー側へ寄せる
- 絞り込み解除チップは「内訳」段の関係する表の直上へ

### 読み込み方針の転換 (FB第3便「信じられないくらい重たい。独立したページを読み込もうとしているから」)

§7 の「見えている段だけ取得」を撤回し、**データを段でなく期間に紐づける**:

- キャッシュキー = 期間+フィルタ (excludeSynthetic / includeSidechain / granularity 等)。
  キーが同じ限り、**段の切替では 1 本もリクエストを発行しない** (即時表示)
- キーが変わったとき: 可視段のデータを最優先で取得 (減光+更新中表示)、残りの段の集計は
  直後にバックグラウンドで先読みしてキャッシュを埋める (段に入った瞬間には大抵もう有る)
- 要約系 (digest / findings) も同じキャッシュ原則。digest は日付単位キー
- LLM 明示起動の契約は不変 (先読みは SQL 集計のみ。LLM は絶対に先読みしない)
- ポーリング (index/summarize 進行中) は可視段のみ更新で従来どおり

## 8.8 v7 改訂 (2026-08-14 — 取り込み速度と会社別判別・宮崎さんFB第4便)

FB:「取り込みに異様に時間がかかる」「各社モデルの種別分けで判別とかはしてほしい」

### 取り込み (インデックス) の速度

- **計測が先**: 再インデックス1回のフェーズ別時間 (走査 / パース / DB書き込み / 要約後処理) を
  実測し、支配項を特定してから直す。推測での最適化はしない
- 増分性の検証: 既読ファイル (size/mtime 不変) を再パースしていないか。していれば増分をまず直す
- DB 書き込みはトランザクション束ね・prepared statement 再利用を確認
- 目標: 増分再インデックス (新規分のみ) を数秒台、初回フルも現状から体感半減

### 会社 (プロバイダ) 判別

- モデル名から決定的に判別: `anthropic` (claude-*) / `openai` (gpt-*) / `google` (gemini-*) /
  `local` (ollama/ 等) / `other`。判定ルールは price 分類 (§8.6) と同じ1か所の定数表に統合
- 「まとめ方」に **会社** を追加: `まとめ方: 会社 / 系統 / モデル` (日別チャート・モデル別表に効く)
- 画面表示は日本語にしない (社名は固有名詞: Anthropic / OpenAI / Google / ローカル / その他)
