## 2. 先行研究 — Blackboard architecture

この設計には名前がある。**Blackboard architecture (黒板モデル)** — エージェントが直接通信せず、構造化された共有ワークスペースを介して間接的に相互作用し、中間的な仮説・制約・部分解を段階的に積み上げる協調アーキテクチャ。1970 年代からあり、2026 年に LLM マルチエージェントの文脈で再興している。

| 出典 | 借りるもの |
|---|---|
| [LLM-Based Multi-Agent Blackboard System](https://arxiv.org/abs/2510.01285) | 中央が黒板に投稿し下位が能力ベースで自発応答する。調整役が各エージェントの専門性を事前に知らなくてよい |
| [PatchBoard: Schema-Grounded State Mutation](https://arxiv.org/pdf/2605.29313) | 黒板への書き込みを schema で接地し、監査可能性を担保する |
| [Beyond Self-Talk (survey)](https://arxiv.org/pdf/2502.14321) | MetaGPT が黒板パラダイムで状態更新・コード片・課題解決を投稿する実装例 |
| Generative Agents (Stanford) | memory stream に観測を積み、reflection で高次の洞察を生成する。母艦の正本は reflection に相当 |
| Stigmergy (アリの経路形成) | 個体が環境に痕跡を残し他個体が読む。直接通信のない協調の原型 |
| ADR / 航海日誌 / ラボノート | 追記のみ・改竄しない・出典つき |

**先行研究との決定的な違い**: 既存の黒板モデルは**エージェント同士の協調**が目的で、人間は系の外にいる。この設計は**人が読むこと**が第一目的である。判断基準は「宮崎さんが 30 秒で状況を掴めるか」であって、エージェント間の情報伝達効率ではない。AI 同士の連携は副次的な利得。

Oracle 裁定「エージェント同士の直接会話は禁止」(WorkOrder 設計) は、黒板モデルの「直接通信しない」原則と独立に同じ結論へ到達していた。

## 3. 確定した設計 (論点 1〜4)

### 3.1 家は役割・レーンごとに 1 軒 <span>(論点 1)</span>

「mycmux 実装」「モモスタ図版」のような**仕事の単位**で 1 軒。セッション (タブ) が死んでも家は残り、次の子が書き継ぐ。歴代の住人が記録される。

セッション単位にしない理由 = 数が多く、閉じたら家も消える。案件単位にしない理由 = 家が大きすぎて「おのおのが何をしているか」が見えない。

### 3.2 発信は自動が骨・AI が肉 <span>(論点 2)</span>

**この分け方の根拠は「誰が知っているか」である。**

| 種類 | 中身 | 誰が知っているか |
|---|---|---|
| **骨** | コミット・テスト結果・停止・終了 | **機械**。observation から取れる |
| **肉** | 何が分かったか・どこで詰まったか・なぜそう判断したか | **AI だけ**。外から観測できない |

肉は AI の中にしかない。hook がどれだけ正確に節目を検出しても、AI が「言うことがない」と思っていれば薄い投稿しか出ない。逆に「仕様の穴を見つけた」瞬間は外から見えない — その時エージェントは、外から見ればただファイルを読んでいる。

**節目 ≠ 価値ある瞬間。** この 2 つを同一視したのが v0.42 の構造的失敗だった。「セッションが完了しました」は節目だが価値はゼロ。

### 3.3 他の AI は読む + 自分の家から言及する <span>(論点 3)</span>

よその家を読める。返事は**自分の家に書き、相手を参照する**。直接会話ではないので Oracle 裁定を破らず、やり取りが公の場に残って人が後から辿れる。参照は両方の家に出る。

相手の家に直接書き込む (コメント欄) 案は却下 — 実質的に直接会話へ近づく。

### 3.4 母艦がゲートになる <span>(論点 4)</span>

```
hook (Claude / Codex / Grok)
   → 機械の一次判定 (決定的なふるい)
   → 母艦が「書かせる価値があるか」を判断
      → 要る  → 子 AI が自分の言葉で報告を書く → 家に載る
      → 要らない → 骨だけ残して黙る

骨 (コミット・テスト・停止・終了) はゲートを通らず必ず家へ
```

母艦の一段前に機械の一次判定を置くのは、全 hook イベントを母艦に流すと母艦のコンテキストが生素材で埋まるため (文脈コスト規律)。

この形が 4 つの単純案の欠点を全部消す。

| 単純案 | 欠点 | この形での解消 |
|---|---|---|
| hook が促す | 言うことがない瞬間にも書かせて水増しする | 母艦がふるう。無価値な促しは子に届かない |
| AI 任せ | 書き忘れる・ムラが出る | 母艦が節目を捉える。忘れても声がかかる |
| 母艦が代筆 | 家がその子の場所でなくなる | 書くのは常に子 AI 本人 |
| 定期に促す | 作業を中断させる・同じ内容が並ぶ | 母艦が要否を判断。無駄な中断がない |

**hook は既に 3 エージェントすべてに入る** (`f462bfbd`・未リリース): `~/.claude/settings.json` / `~/.codex/hooks.json` + `config.toml` / `~/.grok/config.toml`。Codex は trust を位置で決めるため既存グループの後ろに追加する配慮も入っている。

### 3.5 母艦の役割は 3 つ、禁止が 1 つ

宮崎さん (2026-08-31): 「母艦が家の管理整理していかんと崩壊しそう。母艦が予測して書くのは NG だけど、正本としておくべきルールは母艦が書くべき。その家としての全体を考慮した、俯瞰した目線での管理が必要」

1. **ゲート** — 肉を書かせるかの判断 (§3.4)
2. **正本を書く** — ルール・裁定・決定事項。この家で何が決まっているか
3. **管理・整理** — 俯瞰して家を整える

**禁止: 予測して書かない。**

| | 母艦が書く | 子 AI が書く |
|---|---|---|
| 書いてよい | 決まったこと・裁定・ルール・この家の現在地 | 自分がやったこと・分かったこと・詰まったこと |
| 書いてはいけない | 子が何をしたか・何を考えたかの**推測** | — |

母艦が書けるのは確定した事実と、自分が下した判断だけ。子の内面や作業内容を代弁した瞬間に予測が混ざる。

### 3.6 家の構造 — 正本と流れの 2 層

```
【mycmux 実装】               ← 名札
──────────────────────────
■ 正本 (母艦が書く・俯瞰)
   この家の目的 / 現在の到達点
   決まっているルール・裁定
   次にやること
──────────────────────────
■ 流れ (時系列・下に積む・append only)
   骨 = 自動 (コミット・テスト・停止)
   肉 = 子 AI 本人の言葉
   参照 = よその家への言及
```

上が Wiki、下がタイムライン。「日報でもありブログでもあり家でもあり名札でもある」がこの 2 層で成立する — 名札 = 正本の先頭、日報・ブログ = 流れ、家 = その両方を持つ場所。

流れだけの家は 3 日で読めなくなる。正本が上にあって「いま何が決まっているか」が一目で分かるから、下の流れが読み物として意味を持つ。

## 4. 設計原則 — AI の性能向上への耐性

### 4.1 ゲートを構造に埋め込まない <span class="chip ng">最重要</span>

母艦のゲートは、**子 AI が賢くなれば不要になる可能性が高い**。子が「これは書く価値がある」を自分で判断できるようになれば、ゲートは中間の遅延でしかなくなる。

したがって **書き込み経路は子が直接持ち、母艦のゲートはその経路を「促す」側に置く**。「子 AI は母艦経由でしか書けない」と実装すると、子が賢くなったときに作り直しになる。この形なら promote/demote が設定 1 つで済む。

**これは今決めればコストゼロ、後から直すと作り直し。**

### 4.2 部品ごとの耐性

| 部品 | AI が賢くなると | 方針 |
|---|---|---|
| 母艦のゲート | 不要になる可能性が高い | 外せる構造にする (§4.1) |
| 機械の一次判定 | 賢い母艦なら直接捌けるが、コストは残る | 残す。性能でなくコストの問題 |
| 母艦の正本執筆 | 質は上がる。役割は消えない | 残す |
| 骨 (観測) | **性能と完全に無関係。永久に必要** | 土台として最優先で作る |

### 4.3 いまの性能でも動く根拠

1. **2026-08-31 のセッションで人手で同じ流れを回した。** Codex が仕様の穴を見つけて止まり、母艦が裁定して ADR に書き、Codex が読み直して実装した (`56d6368c`)。これは §3.4 の流れそのもの。人手で回したものを仕組みにするだけなので、必要な知能水準は既に足りている
2. **失敗しても骨が残る。** 肉の質が低い時期でも家は成立する。「このレーンは 3 時間コミットがない」は骨だけで読める

### 4.4 性能が上がっても解決しないもの

- 母艦のコスト。判断が増えれば課金も増える
- 人が読む時間。家が 10 軒あれば読む時間は 10 倍。これは **UI の設計**が解く問題 (§5.6 の横断ビュー)
- 人が書く場所がない → §5.1 で解決 (母艦が引用 + 人も書ける)

## 5. 確定した設計 (壁打ち後半・2026-08-31)

### 5.0 論点 1 の詰め — 「役割」と「レーン」は寿命が違う

同じ「レーン」という語で 2 つのものを呼んでいた。

- **役割** = 「mycmux 実装」。終わらない。便が積まれ続ける
- **便** = 「attention-order」。1 便で終わってタブを閉じる

**家は役割に建てる。** 便はその家に積まれる投稿であって、家ではない。家一覧に「歴代 4 人目・通算 19 便」と出るのはこのため。したがって家はめったに終わらず、§5.2 の「休眠」が実際の論点になる。

### 5.1 人の裁定は母艦が引用し、人も直接書ける

既定は**母艦が引用**する。宮崎さんが裁定を下したら、母艦がそれを見つけて正本に引用で残す。人の手間はゼロ。2026-08-31 のセッションはこの形で機能した (裁定 → 母艦が ADR に書く)。

ただし母艦が「これは裁定だ」と気づかなければ落ちるので、**人が直接書ける道を安全弁として残す**。

引用と代弁の線引きは §3.5 の禁止事項がそのまま効く。宮崎さんの言葉をそのまま引くのは事実の記録、意図を推し量って書くのは予測。

### 5.2 動きが止まった家は休眠して沈む。消さない

一定期間動きがなければ一覧の下へ沈めて畳む。動きが戻れば自動で上がる。**可逆で、履歴を失わない。**

自動アーカイブ (別の場所へ移す) は採らない — 基準が難しく、探すときに一手間増える。人が明示的に畳む方式も採らない — 畳む手間が残る。

### 5.3 母艦が見ていない間のイベントは溜める。上限を超えたら骨へ

母艦が次に来たときまとめて判断する。ただし溜まりすぎると母艦のコンテキストを食うので、**一定数を超えた分は古いものから骨だけに落とす**。

時間で自動的に書かせる案は却下 (水増しが戻る)。母艦不在なら骨だけという案も却下 (重要な発見を取り逃す)。

### 5.4 一次判定が母艦に上げるもの

**骨は全部自動で家に載る** (判断不要)。そのうち母艦に上げて「肉を書かせるか」を検討させるのは次の 3 種。

| 種類 | 例 |
|---|---|
| **結果が出た瞬間** | コミット / テストの緑・赤 / 委譲の受理・差し戻し |
| **止まった瞬間** | 長時間停止 / エラー終了 / 質問待ち |
| **変化の規模** | 大きな差分・多数ファイル変更 |

「始まりと終わり」(セッション開始・終了) は上げない。骨として必ず残るので、母艦の判断を要しない。

<div class="callout warn">「変化の規模」には注意が要る。規模と価値は相関しない (<code>cargo fmt</code> が 200 ファイル触っても中身はゼロ)。<b>単独条件にせず</b>、「規模が大きく、かつまだ結果が出ていない」のような組み合わせにする。</div>

### 5.5 正本は各行に出典を必須にする

母艦は LLM なので、放っておけば推測を書く。2026-08-31 に母艦自身が実例を作った — コードを読む前は「rank と attention rules のどちらが勝つか未定義」と書いていたが、実際は「捨てていた」だった。正本に書いていたら誤った正本が残っていた。

**正本の 1 行ごとに根拠を紐づけ、出典のない行は書けない。** 機械的に弾けるので決定性がある。先行研究の PatchBoard (schema-grounded state mutation) と同じ方向。

出典の型は 4 つ:

| 型 | 例 |
|---|---|
| 実測 | `session_board.rs:275` |
| 人の発言 | 宮崎 (8/31) |
| コミット | `56d6368c` |
| 母艦の裁定 | 母艦の裁定 (8/31) |

書式で縛る案 (断定形のみ許可) は却下 — 断定形の嘘は通ってしまう。引用元がある場合のみ書ける案も却下 — 母艦自身の裁定が書けなくなる。

### 5.6 横断して見る手段は 3 つ

家一覧 (各家の最新 1 行) を基本として、次を足す。

1. **全文検索** — 「あの件どうなった」を探す。正本も流れも横断して引ける
2. **全家混合の時系列** — 全レーンの発信を 1 本の時間軸に混ぜる。今何が起きているかを見る
3. **母艦が書く「今日のまとめ」** — 1 日の終わりに全家を俯瞰して 1 枚

「要対応だけの絞り込み」は採らない。既存の attention カードと役割が重なり、同じものが 2 か所に出る。

### 6.1 失敗が残る保証がない (未解決)

「分かったこと」は書きやすく「やらかしたこと」は書きにくい。放置すると成功だけが並ぶ家になる。2026-08-31 に母艦が send を誤診断して二重送信した件を家に書く動機は、構造上どこにもない。失敗こそ次の人の役に立つので扱いが要るが、**どう仕組みにするかは未定**。

## 7. いいところ・わるいところ

**いいところ**: 骨と肉の分離が「誰が知っているか」に基づくので境界が揺れない / 母艦が止まっても骨は残り家は死なない / 既存資産 (hook 3 エージェント対応・ADR 形式・observation 契約・socket API) にそのまま乗る / 直接会話禁止を守ったまま連携が成立 / 2 層構造で読みやすさと網羅性が両立。

**わるいところ**: 母艦への依存が強く、ゲート・正本・整理の 3 役すべてが母艦 / 母艦のコストが家の数に線形 / 「書く価値」の判断が主観的で後から検証できない / 正本の更新タイミングが曖昧だと腐る / 作るものが多く、一度に作ると v0.42 を繰り返す。
