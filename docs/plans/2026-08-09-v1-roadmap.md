# mycmux 1.0.0 ロードマップ (v0.21.29 → 1.0.0)

## Context

v0.21.29 時点で機能面は充実したが、宮崎さんの課題認識は3点: ①iPhone 連携が雑い ②タブを整理したあと「どこで何が動いているか」を見失う ③Chrome タブ級の自由度が欲しい。3本の全数監査 (iPhone 連携実態 / タブUXギャップ / 1.0 readiness) と 2026 年の外部潮流調査 (Claude Code 純正 Remote Control・Tactic Remote/Nimbalyst 系モバイル操作アプリ・amux/Agent View 系 mission control UI) を実施済み。

**宮崎さん決定 (2026-08-09 AskUserQuestion):**
- iPhone = 自前 PWA 全面刷新 (Codex/hybrid も扱えるのは自前だけ)
- タブUX = マルチウィンドウ切り離し + 並べ替え/閉じ取りこぼし修正/ワークスペース色
- 品質 = 安定・安全系のみ 1.0 前に先行、大型リファクタ (契約テスト振る舞い化・E-4/D-4 分割) は 1.x

## 監査で確定した主要事実 (根拠)

### iPhone 連携 (雑さの正体)
- 自前 axum サーバ (port 7682) + PWA は存在するが **2026-05-05 から凍結** (`src-tauri/src/remote/client/`)
- 正規の status feed (`/ws/status`) が**実装・公開済みなのに消費者ゼロ** — スマホは生バイトの正規表現で状態を当て推量 (`app.js:80-110`)
- 承認ボタンは鮮度ガードなしで `y\n` 直送 (socket.rs の `expected_session_epoch` 系ガード不使用)
- スマホの resize が PC の実 PTY を書き換える (`ws_handler.rs:227-233`)
- push 通知なし / TLS なし (トークンをクエリ文字列で平文 HTTP) / 単一静的トークン・端末別失効不可
- 再接続のたび 256KB スクロールバック全量再送 / 「+New」は PC から見えないプロセス単位シングルトンシェル
- remote/ 約1,500行にテストほぼゼロ (auth.rs のみ)

### タブUX (見失いの正体)
- **「どこで何が開いているか」に答える画面が存在しない**: CRSM (Ctrl+P) は履歴検索で開いているタブへ飛べず常に新ペインを増やす。Tab Sweep は掃除専用でナビ不可・検索欄なし
- Ctrl+Shift+T が**ピル×とワークスペース close を記録しない** (`TerminalPane.tsx:494-513` / `AppShell.tsx:540-570` が `closedPaneStore` に積まない)
- ペインタブの**ドラッグ並べ替えなし** (`usePaneDragSource.ts` に index 挿入ターゲットが無い)
- Ctrl+Tab は配列順で MRU でない / マルチウィンドウ非対応 (tauri.conf.json 単一窓)
- `Workspace.color` は**保存されるが描画されない死にフィールド** (`types/workspace.ts:99`)
- サイドバーの cwd/branch は pane[0] 固定・last-log は時刻でなく走査順 (`TabBar.tsx:94-101`)
- 未読 attention リングがサイドバー/タイトルバーへ伝播しない

## 実装フェーズ

### Phase 1 — 品質ゲート (安定・安全系 9件)  [規模 M]
上記採用9件を消化。独立性が高く並列委譲向き。各件に受け入れテストを付ける (B-1 は実機再現手順から)。

### Phase 2 — タブUX小型群  [規模 M]
- ペインタブのドラッグ並べ替え (`resolveDropTargetAtPoint` に index 挿入ゾーン追加 + `reorderTabs` action。pinned は tabs[0] 不変条件と整合)
- Ctrl+Shift+T の取りこぼし修正 (ピル× と workspace close を `closedPaneStore` に記録、復元位置も元ワークスペース優先に)
- ワークスペース色: 死にフィールド `Workspace.color` を活かす (サイドバー行の色バー+タブ帯アクセント+色ピッカー。Chrome tab groups 相当の視覚グルーピング)
- おまけ実益 (監査で判明・小粒): サイドバー last-log を recency 選択に / 未読 attention のサイドバー伝播 / middle-click close

### Phase 3 — マルチウィンドウ切り離し  [規模 L・4段に分割済み]

設計確定 (Plan agent 2026-08-09)。要旨:

**設計を支える発見:**
- **同時 attach は既に構造的に不可能**: `SessionManager::create` の reattach はデータチャネルを置換する (`pty/manager.rs:91-112`) — 「1セッション=1ウィンドウ」の不変条件は輸送層が既に強制。ウィンドウ間移動 = detach/reattach で**respawn 不要・出力ロスなし** (attach epoch 機構がそのまま乗る)
- 直ちに当たる4ブロッカー: ①capability が `"windows":["main"]` で子窓は全 IPC 死 (`capabilities/default.json:4`) ②`socket-request` が全窓 broadcast → コマンド二重実行 ③子窓 close が `quitApp` 直結 ④非リーダー窓はテーマ/ワークスペースを何も hydrate しない
- 状態同期は **シャード済みストア+Rust WindowRegistry+リーダーマージ** を採用 (b: 子=薄いIPCビュー は端末に遅延致命 / c: Rust移管 は XL で棄却)。各窓はフル Zustand を持ち担当ワークスペースだけ保持、子窓は debounce でフラグメントを Rust へ publish、**data.json の書き手は main 1本のまま** `buildSnapshot` が全窓の union をマージ (これを外すとスマホ remote がワークスペースを見失う — 最重要制約)
- ドラッグ切り離しは pointer capture 継続+`screenX/Y` で実現可。**窓をまたぐ真のドロップ (Tier 3) だけが L** で、close=マージ戻し+コンテキストメニュー移動で 9割賄える

**3a — 土台 (S)**: capability glob `mycmux-w*`・`open_child_window` (run_on_main_thread)・`windowContext.ts` (isMainWindow)・socket/close/persist/updater の main-only ガード。子窓 close で quit しないことを確認
**3b — メニュー切り離し (M) = 最小出荷単位**: サイドバー右クリック「新しいウィンドウで開く」。WindowRegistry+フラグメント publish+リーダーマージ+close でマージ戻し。検証: 切り離し中も PTY 出力継続・data.json に全窓分・スマホ remote 全件表示
**3c — ドラッグ切り離し (M)**: ✅ v0.21.34 で出荷。設計から変更: dwell なし・窓外 40px 判定のみ (`src/lib/windowEdge.ts` 純関数)。ワークスペース行ドラッグ (TabBar) とペインタブ/ペインドラッグ (`new-window` ターゲット) の両対応。**同リリースで右クリック凍結を根治** (WebView2 ネイティブメニュー全面抑止・2026-08-09 宮崎さん報告「右クリでフリーズ複数確認・右クリ封印中」) — 以後、右クリック前提の UI 導線は作らない。WS メニューは行ホバーの ⋮ ボタン (左クリック) が正式経路
**3d — 窓レイアウト永続化 (M)**: `WindowConfig` (bounds/workspace_ids/選択) を serde default 追加・schema_version 2・再起動で窓復元・busy カウント全窓化
**Tier 3 (真のドラッグ合流, L) は任意**: Win32 WindowFromPoint hit-test+hover 転送。3b/3c 運用で不足を感じた場合のみ

契約テスト影響は精査済み: socket ガードを JS early-return にすれば `test_socket_api_contract.py` 無傷、`pty/manager.rs:111` の `return Ok(());` ピン (reattach 早期return) は本設計の心臓なので触らない、ほか詳細は設計レポート参照。

### Phase 4 — iPhone PWA 全面刷新  [規模 L・4段に分割済み]

設計確定 (Plan agent 2026-08-09)。要旨:

**設計を変えた発見:**
- socket.rs のフロント橋渡し (`socket.rs:329-463` → `socketCommands.ts` の pane.spawn_tab/close_tab/send_text 等) は**既に全コマンド面が in-process で届く**。`dispatch_to_frontend` を抽出して remote ルートから呼ぶだけ (~80行) でスマホに PC 全操作面が開通 — 「+New シングルトンシェル」バグは修理でなく削除で解決
- 鮮度ガード `stale_send_text_result` (`socket.rs:132-171`) は純関数 — `pub(crate)` 化だけで構造化承認に再利用可
- 再接続 seq 化は `pty/session.rs:740-748` が offset を既に計算済み — broadcast 型を `{data,start,end}` に変えるだけ (消費者2ヶ所)
- `RemoteState` の AppHandle 依存2ヶ所 (`mod.rs:438`/`status_ws.rs:78-82`) を注入化すれば router 全体が #[tokio::test] 可能に
- **注意**: Claude の attention はフロントの画面スキャン由来 (`XTermWrapper.tsx:1057-1147`) — 未マウントタブは waiting がスマホに出ない既存制約。承認キー (`\r`/`\x1b`/数字/矢印の allowlist) は実機検証を Phase 4a 冒頭で行う

**4a — Mission control (M)**: Preact+htm (vendored ES modules・ビルドレス維持・rust_embed)。ホーム=セッション一覧 (`/ws/status` 直結 + 新 `GET /api/sessions` で identity+tail、agent-kind 色バー・状態チップ・未読ドット)。構造化承認 `POST /api/session/{id}/respond` (staleness matrix 対応)。**セキュリティ MUST 同梱**: 端末別トークン (sha256 保存・名前・失効)・Bearer/WS subprotocol 化 (トークンをURLから排除)・120秒ワンタイムペアリングコード QR・サーバ on/off と bind 即時切替・/api JSON 404・レート制限。view mode は **resize しない** (PC のジオメトリを CSS scale 表示)。`remote/session.rs` 削除。manifest icons/apple-touch-icon 修理。テスト: `src-tauri/tests/remote_http.rs` (tower oneshot)・`remote_ws.rs` (tokio-tungstenite)・`tests/test_remote_api_contract.py`・vitest で純クライアントモジュール。`/api/cmd` 橋 (~80行) も 4a に前倒し
**4b — 通知 (S/M)**: `remote/notify.rs` が StatusFeed 購読 → ntfy POST (reqwest 既存依存)。attention_id LRU 重複抑止・attach 中は抑止・`/api/attention/ack` 連動・ペイロード詳細度設定 (既定 title のみ)・毎分上限
**4c — HTTPS+真PWA (S)**: `tailscale serve` で HTTPS origin → service worker・オフラインシェル・ホーム画面インストール完備 (iOS Web Push の前提も整う)。funnel は使わない
**4d — resume/制御ハンドオフ (M)**: `OutputChunk` offset 付き broadcast + `?since=` 差分再送 (256KB 全量再送廃止)・take-control トグル (サイズ復元付き)・スマホから実タブ spawn/close

自前 Web Push (VAPID/aes128gcm, L) は任意・4c 後にだけ検討。各段 DoD = 検証4コマンド全緑 + `docs/features/implemented/remote-pwa.md` 新設。
