## 1. 出発点 — 既にあるもの

白紙ではない。現状を実読して確認した。

| 資産 | 役割 | 場所 |
|---|---|---|
| 画面スキャン | 端末画面から質問を読み `AskScreen` にする | `src/lib/askQuestionScan.ts` |
| 回答の送信 | 数字キーだけを送る (ADR 0003 の実測に基づく) | `askQuestionRouting.ts` の `submitAskQuestionChoice` 他 |
| 送信前の再確認 | 7条件を確認してから送る | 同 `preflight()` |
| 二重送信の抑止 | セッション単位の `inFlight` | 同 `beginSubmit()` |
| カードの土台 | 並べ方・解決 | `AttentionCards.tsx` |
| 置き場所 | 1段で空けた列 | `ReportInbox.tsx` (12行) |

**Phase 2 の本体は新規開発ではなく、検出源の差し替え**である。ただし全部を差し替えられるわけではない (§9.2 で判明)。

```
単一選択・承認:
  いま:  画面を読む       → AskScreen → カード → 数字キー送信
  あと:  hook が構造で届く → AskScreen → カード → 数字キー送信
                                          ↑ここから下は既存のまま

multiSelect:
  検出は hook でできるが、送信はカーソル位置が要るので画面スキャンのまま
```

### 1.1 なぜ差し替えるのか

[ADR 0003](../adr/0003-askuserquestion-input-contract.md) が記録した事実: **Claude の選択肢つき質問は、答え終わるまで transcript に書かれない。** だから記録を追っても質問中は掴めず、画面スキャンで凌いでいる。

画面スキャンの弱点は3つ。末尾16行しか見ていない (質問ブロックは20行を超えることがある)・画面が描画されていないと読めない・レイアウト変更で壊れる。hook なら**質問した時点で構造として届く**ので、いずれも消える。

### 1.2 画面スキャンは捨てない

hook が無い環境 (ランチャーを通さない起動・古い版・未信頼の Codex) では画面スキャンが唯一の手段。hook の契約 §10「劣化させるが止めない」に従い**両方を残す**。優先順位は §5.1 と同じで、hook が高信頼・画面は低信頼のヒント。

## 2. プロンプトの同一性

```
prompt_id            このプロンプト1件を表す
launch_id            どの起動が聞いているか (hook 契約 §4.4)
provider_session_id  provider 側のセッション
turn_id              どのターンの質問か
content_key          質問文と選択肢から導く安定なキー
```

`content_key` は既存の `questionKey(screen)` が同じ役割を果たしている。hook 由来のときも同じ規則で作り、**画面由来と hook 由来で同じ質問なら同じキーになる**ようにする。二重にカードを出さないため。

`launch_id` は Phase 1b の capability から取れる。**画面スキャン由来の質問には無い** — その場合は空とし、§4 の照合では「無いものは照合しない」とする。

## 3. 状態

```
PENDING → ANSWERED     回答が provider へ届いた
        → DECLINED     人が明示的に断った
        → TIMED_OUT    期限切れ
        → STALE        対象が変わって答えられなくなった
        → FAILED       送信に失敗した
```

`PENDING` からのみ遷移する。**一度 `PENDING` を出た prompt は二度と `PENDING` に戻らない。** 同じ内容の質問が再び来たら、それは別の `prompt_id` として扱う。

## 4. 回答の一度きり (CAS)

### 4.1 いま実装されている条件

`preflight()` が送信直前に再確認している7つ。これはそのまま使う。

| 確認 | 意味 |
|---|---|
| `sessionExists` | 対象がまだ在るか |
| `attentionFor(kind === "input")` | いま入力待ちか |
| `contentKey` | 同じ質問か |
| `screenRevision` | 画面が変わっていないか |
| `expectedAttentionId` | 同じ注意イベントか |
| `expectedSessionEpoch` | セッションが張り替わっていないか |
| `expectedInputRevision` | 入力欄が動いていないか |

これが「押した時点でエージェントが終わっていて、答えの文字列がシェルのコマンドとして実行される」事故を防いでいる。

### 4.2 足すもの

**`launch_id` の一致確認を1つ足す。** hook 由来のプロンプトには `launch_id` があるので、送信直前に「いまその起動が current か」を確認できる。起動し直された後に古いカードを押しても届かなくなる。

画面スキャン由来のプロンプトには `launch_id` が無い。**無いものは照合しない** (既存と同じ強度に留まる)。劣化はするが止まらない、の原則どおり。

### 4.3 抑止の粒度を変える

いまの `beginSubmit()` は **セッション単位の `inFlight`**。同じセッションで別の質問が並ぶと片方が待たされる。

**`prompt_id` 単位の CAS に変える。** `PENDING → ANSWERED` の遷移が成功した1回だけが送信に進み、他は `busy` ではなく `already_answered` で静かに終わる。二重クリック・別ウィンドウからの同時回答・遅れて届いた回答が、provider へ二度送られない。

## 5. 3分類の扱い (hook 契約 §2)

| 分類 | エージェントを待たせるか | Phase 2 で実装するか |
|---|---|---|
| `OBSERVE` | 待たせない | **これだけを使う** (Phase 1b の `hook.observe` をそのまま) |
| `SYNC_DECISION` | 待たせる | **しない** — hook の timeout が数秒で成立しない (§6) |
| `DEFER_RESUME` | いったん解放して後で答える | しない (Phase 3 送り) |

当初は `SYNC_DECISION` で実装する前提だったが、実測の結果**成立しない**と分かった (§6)。`DEFER_RESUME` は保留の応答形式・再開の経路・保留中に起動が変わった場合の扱いが provider ごとに未調査で、**調べずに契約へ書くと Phase 1b と同じ失敗をする**。

結果として Phase 2 は `hook.observe` だけで足りる。**新しい線の仕様は要らない。**

## 6. 期限 — 待たせる設計は成立しない (2026-08-30 実測で判明)

当初「`SYNC_DECISION` はエージェントを待たせる。既定の期限は60秒」と書いたが、**実装できない**。

実測した事実:

| 対象 | timeout |
|---|---|
| 宮崎さんの既存 hook (`hooks_dispatch.py`) | 5〜12秒 |
| 同 (`feedback-injector` / `skill-hint-injector`) | 3秒 |
| **こちらが登録する hook** (`settings.rs:199`) | **1秒** |

hook の timeout は数秒。**人が質問を読んで押すまでの時間 (数十秒〜数分) を hook の中で待つことはできない。** hook が返らなければエージェントは打ち切って先へ進む。

### したがって Phase 2 は「待たせない」

3分類のうち **`SYNC_DECISION` は Phase 2 では実装しない**。hook は「質問が来た」という事実を即座に報告して 1秒以内に返る (`OBSERVE` と同じ扱い)。人が答えるのは**そのあと別経路** — いまと同じ端末へのキー送信で行う。

```
hook: 「いま質問している」と報告して即座に返る (1秒以内)
  ↓
カード: 質問と選択肢を表示
  ↓
人が押す
  ↓
送信: 端末へ数字キーを送る (既存の経路・§4 の再確認つき)
```

**hook が改善するのは「質問が来たことに気づく速さと確実さ」であって、回答の届け方ではない。** 回答は従来どおり端末経由。

### 期限の扱い

エージェントを待たせないので、mycmux 側の期限はカードの見た目の問題になる。

- カードは**エージェントがまだ入力待ちである限り**表示する。判定は §4 の `attentionFor(kind === "input")` で行う (既に実装済み)
- 入力待ちでなくなったらカードを `STALE` にして**理由を出して残す**。勝手に消さない
- mycmux 側で独自の秒数を決めない。**実態 (端末が入力待ちか) を見る**

### 3分類の再整理

| 分類 | Phase 2 |
|---|---|
| `OBSERVE` | 実装済み (Phase 1b) |
| `SYNC_DECISION` | **実装しない** — hook の timeout が数秒なので成立しない |
| `DEFER_RESUME` | 実装しない (Phase 3 送り) |

**Phase 2 で使うのは `OBSERVE` だけ。** 質問の到来を報告し、回答は既存の端末経路で送る。

## 7. 失敗の方向 (hook 契約 §13 の適用)

| 起きたこと | エージェント | mycmux の状態 |
|---|---|---|
| カードの表示に失敗 | 影響なし | 変えない |
| 回答の送信に失敗 | 影響なし (待ち続ける) | `FAILED` にしてカードを残す |
| 期限切れ | provider の既定動作に任せる | `TIMED_OUT` |
| 対象が消えた | 影響なし | `STALE` にしてカードを残す |

**失敗時にカードを勝手に消さない。** 消えると「答えたつもり」になる。要件書が繰り返し警告している偽成功と同じ形。

## 8. 表示

置き場所は 1段で空けた列 (`ReportInbox.tsx`)。カードの並べ方と解決は `AttentionCards` の仕組みを使う。

- 質問の**本文と選択肢をそのまま出す**。押すだけで答えが返る
- 「開いて答える」は残さない — 手数が減らないボタンが不使用の原因だった
- 答えたカードは消す。答えられなくなったカード (`STALE` / `TIMED_OUT`) は**理由を出して残す**

## 9. 実装前に埋めるもの

### 9.1 判明したこと (2026-08-30 実読)

**注入点は `ingestAskQuestionLines(sessionId, lines, scannedAt, observedInputRevision)`** (`src/stores/askQuestionStore.ts:395`)。画面の行を受け取り `scanAskQuestion()` で `AskScreen` にしてストアへ入れる。`applyScan` の呼び出しはここ1箇所だけ。hook 由来は行ではなく構造で届くので、**同じストアへ入る別の入口**を足す形になる。

### 9.2 送信経路は画面のカーソル位置に依存している — ここが本丸

`AskScreen` / `AskOption` は**画面表示の構造**であって質問の意味構造ではない。

```
AskOption = { index: number|null, label, description?, checked?, current: boolean, role }
                  ↑画面の番号            ↑見た目のチェック  ↑カーソルの位置
```

送信がこれらを使っている:

| 箇所 | 用途 |
|---|---|
| `findNumberedOption` | 画面に振られた番号で選択肢を探す |
| `currentOptionIndex` | **カーソルがいまどこにあるか** |
| `submitAskQuestionMultiSelect` | `submit.current` を見て `↓` を何回押すか決める |

**hook はカーソル位置を持たない。** provider が「いま何行目にカーソルがある」とは報告しないため。

つまり「hook 由来の構造をストアに入れれば下流はそのまま動く」という当初の見立ては**誤り**だった。単一選択 (数字キー1回で確定) は番号さえ分かれば送れるが、**multiSelect は画面を見ないと送れない**。

### 9.3 したがって Phase 2 の範囲を絞る

| 種類 | hook 単独で送れるか | Phase 2 で扱うか |
|---|---|---|
| 単一選択 | ○ (番号を押すだけ) | **扱う** |
| 承認 (許可/拒否) | ○ (番号を押すだけ) | **扱う** |
| multiSelect | **×** (カーソル位置が要る) | **扱わない。画面スキャンのまま** |

multiSelect は hook で**検出**はできる (質問が来たことは分かる) が、**送信は画面スキャン経由に落とす**。両方が揃っているときだけカードから答えられる、という形になる。

これは劣化ではない。いまも multiSelect は画面スキャンでしか送れていない。**hook で改善するのは単一選択と承認の検出精度**であって、multiSelect の送信手段ではない。

### 9.4 残る宿題

- ~~`hook.prompt.*` の線の仕様~~ → **不要になった** (§6)。Phase 2 は `hook.observe` だけで足りる
- ~~provider ごとの期限の実測値~~ → **不要になった** (§6)。期限は端末が入力待ちかで判定する
- hook 由来の質問から `AskScreen` 相当を組み立てるとき、`index` をどう決めるか (provider が選択肢の順序を返すなら 1 始まりで振れるか要確認)
- `content_key` を hook 由来でも同じ規則で作れるかの確認
