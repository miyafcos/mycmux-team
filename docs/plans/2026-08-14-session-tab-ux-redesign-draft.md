## 2. 「立てたつもり」を構造で潰す — 3段

摩擦を消す → 器を置く → 差分を常時見せる、の順でしか潰れない。どれか1つでは漏れる。

1. **摩擦を消す**: 選択テキスト・チャットの一節・思いつきの1行から、**1アクションで立てられる**
   (spec ファイル作成を挟まない。書いた文がそのまま最初の指示になる)
2. **器を置く**: 立てる前の予定を保持する第一級オブジェクトを作る (下記2案)
3. **差分を見せる**: 立てていない予定が**画面に残り続ける**。消えるのは立てたときか、捨てたときだけ

### 器の案 — 2案 (どちらもデータモデルは共通)

**案① 「まだ立ててない」タブ**
タブバーに点線枠のタブを置く。クリックで立つ (書いた文がそのまま最初の指示になる)。
エージェントからも `pane.declare_tab` で置ける — 「隣で考えます」と言った瞬間に枠ができ、
立て忘れたら点線タブが残って一目で分かる。この RPC は実行を伴わないので安全に自動化できる。

- 長所: 「立てたつもり」が物理的に見える。起動が1クリック。既存のタブ操作 (ドラッグ・ピン留め・閉じる) をそのまま流用
- 短所: タブバーの本数を食う。予定が溜まると幅が死ぬ (現行 `PANE_TABBAR_*` は既に7段の縮退モードを持つ)

**案② 「まだ立ててない」の一覧**
タブでなく専用の一覧に積む。行 = やること + 立てる先 (エージェント/cwd) + 立てる + 捨てる。
1件でもあればサイドバーに件数を出す。

- 長所: タブバーを汚さない。予定だけ先に積む運用 (計画→まとめて着手) に合う
- 短所: もう1つ画面が増える (P-3 の分散を悪化させる)。見に行かないと気づかない → バッジ設計が生命線

推奨: **①を主、②を①の「畳んだ表示」として同じデータで実装**。1本なら点線タブ、
3本以上に増えたら1枠に畳んで「まだ 3」と出す。畳んだ枠を開くと②の一覧になる。

## 3. 俯瞰と一括操作 — UI 方向2案

**案A 盤面 (Board) — 俯瞰面を1枚に決める**
`DashboardView` を俯瞰の正面に昇格し、カラム = 状態 (まだ / 動いてる / 待たれてる / 終わった / 落ちた) の
カンバンにする。グループ (§4) は色帯。カラムごと・グループごとの一括クローズ / アーカイブ。TabSweep は
「死」「完了待機」カラムの操作として吸収する。

- 長所: 6グループ+子タブ級の並列に耐える。既存の DashboardView / TabSweepPanel / P1停止検知を1面へ統合でき、P-3 の分散が減る
- 短所: 画面遷移が要る。目の前のペインとの二重管理感。実装量は大きい

**案B タブバー拡張 (In-place) — 視線を動かさない**
タブバーをグループ (§4) 対応にする。グループの色帯 + 折り畳み、親子インデント、
まだ立てていないタブは点線、帯の × でグループごと閉じる。俯瞰はタブバーを縦に展開したドロワー。

- 長所: 視線移動ゼロ、今の操作の延長。データモデル追加 + `PaneTabBar` 改修で届く
- 短所: 幅が本質的に足りない。10本超で縮退モードに落ちて情報が消える (現行の実装が既にその戦いをしている)

推奨: **B のデータモデルを先に入れ、俯瞰は A を後段で乗せる**。両案はデータモデル
(親の記録・まだ立てていない状態) が共通なので、**先にどちらの面を作るかだけが判断分岐**。

> **2026-08-14 宮崎さん裁定: 案B (タブバー拡張) から着手**。グループの色帯・親子インデント・
> 点線の「まだ立ててない」タブをタブバーへ直接入れる。案A の盤面は段2 のデータが揃ってから改めて判断する。

## 4. 語彙と階層 (実装の前にここを固定する)

本書 v1 は「レーン」「宣言タブ」「未起動タブ」を混ぜて使い、v2 は漢語2字で揃えようとした。
前者は層の違うものに同じ語を当てており、後者は**使う人の語彙から採っていない**。
実装でフィールドが増え、画面で言い方が割れる。先に層と語を決める。

### 4-1. 既存の階層に新しい層を足さない

mycmux の階層は **ワークスペース > ペイン > タブ** の3層。ここに「レーン」のような第4層を
差し込むと、移動・保存・閉じるの規則をすべて4層ぶん書き直すことになる。

**まとめは階層でなく関係で表す** — タブが親タブを指し (`origin.parentSessionId`)、
親を根とする木が「ひとまとまりの作業」= グループになる。新しい層は増えない。

- グループの代表 = 根のタブ。グループの名前 = 根のタブの名前 (別名を持たせない)
- グループの色 = 根のタブの sessionId から決定的に決める (人が色を選ぶ操作を作らない)
- 親を持たないタブはどのグループにも属さない。それでよい (手でまとめたい要求が出たら、
  そのとき足すか判断する → Q3)

これで v1 の `lane` フィールドは**不要**になる。データが1つ減り、
「レーンと親子がずれたらどちらが正か」という決めごとも消える。

### 4-2. 画面には宮崎さんの言葉、データには英語

語彙の基準は**使う人が実際に使っている言葉**。設計者の美学 (漢語で短く揃える等) を優先しない。
宮崎さんの原文は「そのペインタブの**たてたり閉じたり**を」— この動詞をそのまま採る。

| 層 | 画面に出す語 | データの識別子 | 使わない語 |
|---|---|---|---|
| 状態 | **まだ立ててない** (短縮表示は「まだ」) | `lifecycle: "declared"` | 「未起動」「宣言タブ」(硬い・実装語) |
| 作る操作 | **あとで立てる** | `pane.declare_tab` | 「宣言する」「予約する」 |
| 動かす操作 | **立てる** | `pane.launch_declared` | 「起動する」 |
| まとまり | **グループ** (画面では代表タブの名前で呼ぶ) | `origin.parentSessionId` の木 | 「レーン」「束」「班」 |

動詞は**タブ=開く / 閉じる**、**セッション=立てる / 終わる**、**作業を渡す=渡す**に固定する。
v1 では「立てる」を画面から締め出していたが、使う人が使う動詞を設計者が禁じるのは逆。
「タブを立てる」と「セッションを立てる」の紛れは、**タブと同時にセッションが立つ**のが実態なので
実害がない (立っていないタブ = セッションも立っていない)。

### 4-3. 「まだ立ててない」タブが答える問い

このタブは「まだ立てていない作業がある」ことだけを言う。**何のための作業かは名前が担う**ので、
作るときにラベルを必須にする (名前の無いものを作らせない)。名前が無ければ結局チャット本文を
読み返すことになり、元の問題が再発する。

## 5. 共通で入れるプリミティブ (どちらの案でも要る)

1. `PaneTab` に追加するのは **3フィールド** (草案の `lane` は §4-1 で不要になった) —
   `origin?: { kind: "human" | "agent"; parentSessionId?: string }` /
   `lifecycle?: "declared"` (既定 undefined = 通常のタブ) /
   `declaredPrompt?: string` + `declaredTarget?: string` (やることの中身。**永続化が要る** —
   `initialPrompt` / `commandArgv` は ephemeral なので流用できない)
   - 永続化・socket シリアライズ・`dedupeAgentSessionsInConfigs` との整合を同時に見る
2. `pane.declare_tab` (作るだけ・PTY を起こさない・**ラベル必須**) /
   `pane.launch_declared` (立てる)
3. `pane.close_tabs` (複数 sessionId・または根の sessionId を渡してグループごと)。既存の close 影響判定
   (`paneCloseImpact.ts` / `paneCloseConfirmation.ts`) を通す
4. spawn 時に親を刻む — `MYCMUX_PANE_SESSION_ID` は既に注入済みなので、`spawn_tab` で
   `origin.parentSessionId` に落とすだけ (`socketCommands.ts:747-814`)
5. 送達確認 (P-8) をタブの表示状態に上げる — 未確認の送信があるタブに印
